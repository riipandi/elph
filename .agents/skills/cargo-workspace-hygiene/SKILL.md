# Cargo Workspace Hygiene

## Language

Split by destination:

- **In-chat responses, plans, summaries** — follow the language the user is currently using (Indonesian, English, etc). Crate names, paths, versions, flags stay literal English.
- **Any documentation edits written to files** (`docs/**`, permanent comments) — **always English**, regardless of chat language.

## Purpose

Keep Elph's dependency graph and `Cargo.toml` files lean without changing runtime
behavior or public package contracts: no avoidable duplicate versions, unused
dependencies, feature-flag creep, or drift from the workspace dependency table.
This is structural dependency hygiene only — not vulnerability/license auditing
(`rust-dep-audit`) and not code-level splitting (`rust-lean-refactor`).

### Elph workspace baseline

Before making assumptions, verify the current metadata. The normal workspace is
the six-package graph containing:

- `elph` (`crates/coding-agent`) — the application, CLI, and main TUI;
- `elph-agent` — the app-agnostic agent runtime;
- `elph-ai` — provider adapters, model catalogs, and public LLM types;
- `elph-tui` — reusable iocraft components (included through a path dependency);
- `floppy` — memory/storage integration;
- `rendown` — terminal/Markdown rendering.

The root `Cargo.toml` uses resolver 2, edition 2024, a large
`[workspace.dependencies]` table, and a local `[patch.crates-io]` override for
`iocraft` under `vendor/iocraft`. `crates/control-plane`, `elph-cron`,
`elph-sandbox`, and other explicitly excluded packages are not automatically
covered by the normal workspace gate; include them only when the user asks.
The former extension packages were removed; do not expect or recreate them
during a dependency audit.

## Scope

- Default scope: the whole workspace's `Cargo.toml` files (root + all member crates), since duplication and unification are inherently cross-crate concerns.
- If the user names a specific crate, still check its deps against the rest of the workspace for duplicates — hygiene issues are relational, not per-crate.

## Safety Rules

- **No version bumps without a call-out.** Deduping to a shared version is only safe when semver-compatible for all consumers; if unifying would force a minor/major bump on some crate, propose it explicitly and let the user decide rather than silently bumping.
- **Unused-dependency removal needs confirmation if it's not obviously safe.** A dep with zero references found by tooling is a strong signal, but re-exports, macro-only usage, or feature-gated code paths can hide real usage — verify before removing, and if genuinely uncertain, ask rather than delete.
- **Use repository wrappers for gates:** run `make fmt`, `make check`, `make lint`, and `make test`. Forward package/feature selectors after `--` (for example `make check -- -p elph-ai`). Use `SCCACHE_DISABLE=1` only when the cache is unavailable or broken; record it in the report.
- **No unprompted tool installs.** If `cargo-machete`/`cargo-udeps`/`cargo-hakari` aren't already installed, ask once before installing (they're dev-only, low-risk, but still an environment change) rather than silently running `cargo install`.
- **One category of change at a time** — don't mix a version-unification pass with a feature-trim pass with an unused-dep removal pass in one unverified diff. Verify gates between categories.
- **Legacy/back-compat deps** (a dep kept only for an old code path) follow the same ask-before-remove rule as other skills — don't fold "unused dependency" and "deliberately-kept-for-legacy" into the same silent bucket.
- **Generated and vendored inputs are not normal source evidence:** do not edit
  `crates/elph-ai/models/**/*.json`, `schemas/`, `vendor/iocraft/`, `target/`,
  build output, or lockfiles generated by a command unless the requested change
  explicitly includes them.
- **Do not destroy parallel work.** Never use `git reset --hard` or a broad
  `git checkout --` to roll back a change. Inspect `git status`, preserve
  unrelated edits, and use a targeted patch or ask when ownership is unclear.
- **Git is opt-in:** do not commit or push unless the user explicitly requests it.

## Workflow

### Phase 1 — Baseline

1. `git status --short` and `git diff --stat`; stop to clarify if unrelated
   changes make ownership ambiguous.
2. Confirm workspace layout with `cargo metadata --no-deps --format-version 1`
   (use Python or manual inspection if `jq` is unavailable). Record package IDs,
   `workspace_members`, `workspace_default_members`, excluded packages, path
   dependencies, patches, and each package's `rust-version`.
3. Run baseline gates through the repository wrapper:
   `make fmt`, `make check`, `make lint`, `make test`. Note pre-existing failures
   and platform-specific failures separately.
4. Check optional tools with `command -v cargo-machete cargo-udeps cargo-hakari`
   or their `--version` commands. Do not install them automatically.
5. Record whether `Cargo.lock` is tracked and whether the baseline commands
   changed it. A hygiene pass must not smuggle an unrelated lockfile refresh
   into a `Cargo.toml` cleanup.

### Phase 2 — Duplicate version scan

1. `cargo tree --workspace --duplicates` (or `cargo tree -d`) at the workspace root — lists every crate pulled in at more than one version.
2. For each duplicate, `cargo tree -i <crate>` to see which members pull which version and why (direct vs transitive).
3. Classify:
    - **Direct + compatible** — two members pin different semver-compatible versions directly → safe to unify via `[workspace.dependencies]`.
    - **Direct + incompatible** — different major versions pinned on purpose or due to a real breaking change upstream → flag for the user, don't force.
    - **Transitive-only** — duplication comes from third-party deps, not the workspace's own choices → usually not actionable; note it, don't chase it.
4. Check whether a duplicate is caused by the local `iocraft` patch, a target
   dependency, a build/dev dependency, or a package with a deliberately different
   MSRV before proposing a change.
5. Produce a list: crate → versions found → members affected → proposed action
   (unify / flag / ignore-transitive), including whether `Cargo.lock` changes.

### Phase 3 — Unused dependency scan

1. Run `cargo machete` if installed; otherwise use `cargo metadata` plus
   `rg`/manual inspection. Treat the result as a candidate list, not proof.
2. Cross-check `src/`, `tests/`, `examples/`, `benches/`, `build.rs`, proc-macro
   attributes, `include!`/`env!`, `pub use` re-exports, and every
   `#[cfg(feature = "...")]` branch. A dependency can be used without a visible
   `use` statement.
3. Check package names versus Rust crate names (`-` becomes `_`) and target
   dependencies separately (`cfg(unix)`, Windows, Linux Wayland, and optional
   features).
4. If `cargo-udeps` is installed and an ambiguous case warrants it, run the
   workspace command with the documented nightly toolchain. Do not install a
   nightly or tool automatically.
5. Classify each finding: **confirmed unused**, **feature/target-gated used**,
   **macro/build/re-export used**, **ambiguous**, or **legacy/back-compat**.

### Phase 4 — Feature-flag audit

1. For each package, inventory `[features]`, `default`, optional dependencies,
   `required-features`, `target.*.dependencies`, and all `cfg(feature = ...)`
   uses. Include examples, integration tests, and `docs.rs` feature settings.
2. Run `cargo tree --workspace -e features` when the graph is available. Check
   default builds separately from feature builds; resolver 2 prevents some
   dev-dependency leakage but does not make every feature combination harmless.
3. Treat `elph-ai` features (`bedrock`, `oauth-callback`, `generate-models`,
   `tracing`), `elph-agent`'s `full`/tool features, Linux-only clipboard
   features, and the local `iocraft` patch as intentional candidates that need
   evidence before trimming.
4. Flag dead features, accidental default features, duplicate optional
   dependencies, and feature combinations that cannot compile on all supported
   targets. Do not introduce `cargo-hakari` unprompted.

### Phase 5 — Unify workspace dependency table

1. For deps used by two or more members at a compatible version, compare the
   package-level declaration with root `[workspace.dependencies]` before moving
   it. Do not unify a dependency merely because the version strings happen to
   match.
2. Preserve package-specific `features`, `optional`, `default-features`, target
   sections, and renamed packages. A member may use
   `dep = { workspace = true, features = [...] }` without flattening all feature
   choices into the root.
3. Respect package MSRV differences: `elph-ai` and `elph-agent` publishable
   crates have their own `rust-version`, while the workspace uses a newer
   development toolchain. A version change that breaks a consumer's MSRV is not
   hygiene-only.
4. Apply one dependency or one small logical group at a time. Run `make fmt`,
   `make check`, and the relevant `make lint`/`make test` gate before continuing.

### Phase 6 — Verify

1. Run `make fmt`, `make check`, `make lint`, and `make test`.
2. Re-run `cargo tree --workspace --duplicates` and the relevant
   `cargo tree --workspace -e features`.
3. Re-run `cargo metadata --no-deps --format-version 1` and inspect the
   `Cargo.toml`/`Cargo.lock` diff. Confirm no generated catalog or vendor file
   changed incidentally.

### Phase 7 — Summary

- **Duplicates found → resolved / flagged**: crate, versions, action taken.
- **Unused deps removed**: crate, member, how confirmed unused.
- **Feature flags trimmed**: flag, member, why dead.
- **Workspace-dependencies unified**: list of deps moved to `[workspace.dependencies]`.
- **Flagged, not touched**: incompatible-version duplicates, ambiguous unused deps, legacy-path deps — with the reason and what a decision would need.
- **Gate status**: pass/fail per gate, workspace-wide, including whether
  `SCCACHE_DISABLE=1` or a platform-specific selector was required.

## Notes

- This skill doesn't run `cargo audit` or license checks — that's `rust-dep-audit`. If the user wants both, run this one first (structural cleanup can change which versions exist, which changes what the audit sees).
- Transitive-only duplicates from third-party crates are usually not worth chasing — don't manufacture busywork trying to eliminate them.
- Respect existing workspace conventions (e.g. if some members intentionally pin an older version for compatibility with an external consumer) — ask rather than "fixing" what might be deliberate.
- Git: do not commit or push unless explicitly instructed. Keep each logical
  change separable in the working tree so the user can review or commit it.

## Example

User: "check this workspace's dependencies, are there any duplicate versions, are there any unused ones, just unify them into workspace.dependencies"

Agent workflow:

1. Baseline gates + `cargo tree -d` + tool availability check.
2. Phase 2: classify duplicates (unify-safe vs flag vs transitive-noise).
3. Phase 3: `cargo machete` + manual cross-check for false positives.
4. Phase 4: dead feature flags.
5. Phase 5: move shared deps to `[workspace.dependencies]` one group at a time, gate-check between groups.
6. Phase 6–7: final verify + summary with what got flagged for a decision.
